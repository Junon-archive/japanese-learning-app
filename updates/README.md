# updates --- 변경 요청 관리

## 이 폴더의 지위

`updates/`는 **변경 요청**을 모으는 곳이다. **명세가 아니다.**

-   구현의 source of truth는 `spec/`이다. 요청서는 구현 근거가 되지 않는다.
-   요청은 spec-sync가 `spec/`에 반영한 뒤에만 구현한다(`AGENTS.md`).
-   요청서와 `spec/`이 충돌하면 구현하지 않고 멈춰 보고한다. 명세 변경은 spec-sync를 거친다.

## 파일

``` text
updates/
├── README.md          이 문서
├── ROADMAP.md         전체 요청 목록과 상태
├── _TEMPLATE.md       요청서 양식
├── backlog.md         MVP-01에서 다음 사이클로 미룬 항목
├── U-NNN-<slug>.md    요청서 (참고자료 없음)
├── U-NNN-<slug>/      요청서 (참고자료 있음)
│   ├── request.md
│   └── refs/
└── done/              완료된 요청서
```

## 요청서 작성법

1.  `_TEMPLATE.md`를 복사해 새 번호로 만든다(아래 `번호와 파일 이름`).
2.  **사용자**가 머리 정보와 사용자 절 다섯 개를 쓴다.
    -   배경: 왜 필요한가
    -   원하는 것: 무엇이 달라져야 하는가
    -   원하지 않는 것: 바뀌면 안 되는 것, 범위 밖
    -   참고: 참고 사이트, 이미지, 관련 요청
    -   완료 확인 방법: 무엇을 보면 끝났다고 판단하는가
3.  **Claude**가 Claude 절 세 개를 쓴다.
    -   영향 명세·충돌: 바뀌어야 하는 `spec/` 문서와 조항, 충돌하는 조항
    -   결정 필요 질문: 사용자가 답해야 진행할 수 있는 것
    -   작업 계획: Wave와 레인 대응
4.  사용자 절은 사용자가 결정한 내용만 적는다. Claude는 사용자 절에 새 정책을 더하지 않는다.
5.  완료 확인 방법은 판단 기준을 적는다. 정식 합격 기준은 spec-sync가 해당 마일스톤의
    `13_ACCEPTANCE_CRITERIA.md`에 둔다.

## 처리 흐름

``` text
요청 → 영향 분석 → 결정 → spec-sync 반영 → 구현 → 게이트 → 커밋 → 배포 → 완료
```

-   **영향 분석:** Claude가 요청서의 Claude 절을 채운다.
-   **결정:** 결정 필요 질문에 사용자가 모두 답한다.
-   **spec-sync 반영:** 결정 내용을 `spec/`에 반영하고 `spec/CHANGELOG.md`에 기록한다.
    되돌리기 비싼 결정은 `docs/decisions/`에 ADR로 남긴다.
-   **구현:** `spec/`만 근거로 구현한다.
-   **게이트:** 해당 마일스톤의 게이트를 통과한다.
-   **커밋:** 게이트를 통과한 결과를 main에 커밋한다. 이 시점이 `배포 대기`다.
-   **배포:** 사용자가 한다. 에이전트는 배포하지 않는다.
-   **완료:** 사용자가 배포를 확인한 뒤 `완료`로 바꾼다.

## 상태

``` text
요청됨 → 분석됨 → 결정됨 → 명세 반영 → 구현 중 → 배포 대기 → 완료
```

| 상태 | 뜻 |
|---|---|
| 요청됨 | 사용자 절이 작성되었다 |
| 분석됨 | Claude 절이 작성되었다. 결정 필요 질문이 남아 있을 수 있다 |
| 결정됨 | 결정 필요 질문이 없다. 명세 반영 전이다 |
| 명세 반영 | spec-sync 반영이 main에 커밋되었다 |
| 구현 중 | 구현을 시작했다 |
| 배포 대기 | 게이트 통과 후 main에 커밋되었다. 사용자 배포 전이다 |
| 완료 | 사용자가 배포를 확인했다 |
| 보류 | 나중에 다시 본다. 종결 상태가 아니다 |
| 검토 후 유지 | 종결. 검토했고 현재 동작을 바꾸지 않기로 했다 |

-   종결 상태는 `검토 후 유지` 하나다.
-   요청서의 `상태`와 `ROADMAP.md`의 `상태`는 같이 바꾼다.

## 번호와 파일 이름

-   번호는 `U-NNN`(세 자리, `U-001`부터)이다. **한 번 쓴 번호는 재사용하지 않는다.**
    보류·검토 후 유지가 된 번호도 다시 쓰지 않는다.
-   파일 이름은 `U-NNN-<영문 kebab slug>.md`다.
-   참고자료가 있으면 디렉터리 `U-NNN-<slug>/`를 만들고 요청서는 `request.md`, 참고자료는 `refs/`에 둔다.
-   요청서 없이 결정만 기록하는 행은 `ROADMAP.md`에서 번호를 `-`로 둔다.

## done/ 이동

-   `완료`가 된 요청서를 `done/`으로 옮긴다. 디렉터리 형태는 디렉터리째 옮긴다.
-   옮겨도 **파일·디렉터리 이름을 바꾸지 않는다.**
-   옮긴 뒤 `ROADMAP.md`의 링크만 새 경로로 고친다.

## 공개 저장소 주의

이 저장소는 공개 상태다. 요청서, `refs/`, ROADMAP, backlog 모두 커밋되므로 다음을 쓰지 않는다.

-   API 호스트명
-   외부 연결 경로를 여는 서비스의 이름과 설정 이름
-   포트
-   서버 경로
-   IP
-   계정 ID
-   secret(API key, password, token, `.env` 값)

실제 도메인도 쓰지 않는다(`docs/decisions/ADR-020-production-topology.md`의 결정 6).
README의 사이트 주소 1개는 예외다. 근거는 ADR-020 결정 6 개정(2026-09-13)이다.
