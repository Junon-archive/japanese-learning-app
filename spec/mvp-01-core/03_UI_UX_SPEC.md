# UI/UX Specification

Reference: `spec/reference/ui/core-learning-mockup.html`. 기능/상태
명세가 목업보다 우선한다.

MVP-02 화면(선택 홈, 상단바, 설명 시트, demo, 가나 학습)의 reference는
`spec/reference/ui/mvp-02-mockup.html`이다. 두 목업이 다르면 MVP-02 목업을 따르고,
어느 목업이든 이 문서와 다르면 **이 문서가 우선한다**(`spec/reference/ui/README.md`).

**MVP 레이아웃은 단일 컬럼이다.** 모바일이 주 사용 환경이므로(아래
`Study Screen`) mockup의 사이드바는 MVP 구조가 **아니다.** 이 문서가
`사이드바의 ...`라고 적은 곳은 mockup 안에서의 위치를 가리키는 말이며 그
구조를 만들라는 뜻이 아니다. 화면 사이 이동은 각 화면 안의 링크·버튼으로
한다(`History`의 `학습으로 돌아가기`, `Study Screen`의 `학습 기록`).
MVP-02에서 여기에 **모든 화면 위의 상단바**가 더해진다: 앱 이름을 누르면 선택 홈, 공개
화면의 `로그인` 진입점, 로그인한 화면의 `학습 기록`·`로그아웃`(아래 `상단바`). `Study Screen`의
`학습 기록`은 이 상단바로 옮겼다. 단일 컬럼 규칙은 그대로다.

## 문구 가이드

화면에 보이는 모든 문구(텍스트, 버튼, 라벨, `aria-label`, 안내, 오류)에 적용한다. **말투만
다룬다.** 폰트는 범위 밖이다. 학습 콘텐츠(설명의 `core_meaning`, `nuance`, 예문, 번역 등)는
seed·LLM이 만든 **데이터**라서 대상이 아니다. 화면이 조립하거나 고치지 않는다.

### 우선순위

1.  **보안 문구 규칙이 말투보다 먼저다.** 로그인 실패는 사유를 가르지 않는 한 문구다
    (`Login`). 말투를 다듬다가 "없는 아이디"와 "틀린 비밀번호"를 가르거나 정보를 더하지
    않는다.
2.  **이 문서가 동작과 함께 고정한 문구**(아래 표의 `고정`)는 그 절이 canonical이다. 표기를
    바꾸려면 그 절을 먼저 고친다. 말투 때문에 뜻을 바꾸지 않는다.
3.  **서버가 준 숫자만 화면에 쓴다**(`진행 표시`). 말투를 다듬으면서 분 수·횟수·상한을
    새로 적지 않는다.
4.  그다음이 아래 원칙 여섯 개다.

### 원칙

1.  **해요체.** 안내문은 `~해요`, `~예요`, `~있어요`로 끝낸다. `~합니다`, `~한다`, 명사로
    끝나는 안내문을 쓰지 않는다. 버튼·라벨처럼 짧은 이름은 명사형(`다음 문장`, `로그아웃`)이나
    `~하기`(`다시 시도하기`)를 쓴다.
2.  **한 문장에 한 정보.** 쉼표·`~며`·`~고`로 두 사실을 잇지 않는다. 필요하면 문장을 나눈다.
3.  **짧게.** 한 문장은 대체로 25자 안팎을 넘기지 않는다. 버튼은 2\~6자.
4.  **탓하거나 재촉하지 않는다.** 사용자가 잘못했다고 읽히는 말, 서두르게 하는 말(`지금 바로`,
    연속 일수, 밀린 복습 수)을 쓰지 않는다. 틀린 답에도 사실과 다음 일만 말한다. overdue/streak
    punishment 금지와 같은 취지다.
5.  **전문용어 대신 쉬운 말.** 내부 개념어를 드러내지 않는다: `세션` → `학습`, `노출` →
    `본 횟수`, `요청`/`서버`/`API` → `연결`, enum 값(`word`) → 우리말 라벨. 내부 id는 계속
    노출하지 않는다. 학습 대상 자체의 이름(`후리가나`, `히라가나`, `탁음`, `요음`)은 그대로
    쓴다.
6.  **할 수 있는 행동을 알려준다.** 안내·오류 끝에는 사용자가 할 수 있는 일을 적거나 버튼을
    붙인다. 할 수 있는 일이 없으면 그 사실을 적는다(무한 대기처럼 보이게 하지 않는다).

| 원칙 | 좋은 예 | 나쁜 예 |
|---|---|---|
| 1 | 저장하지 못했어요. 다시 시도해 주세요. | 저장 실패. 재시도하십시오. |
| 1 | 아직 학습 기록이 없어요. | 학습 기록 없음 |
| 2 | 체험 중이에요. 기록은 이 브라우저에만 남아요. | 데모 모드이며 실제 계정이 아니고 기록은 이 브라우저에만 저장됩니다. |
| 3 | 오래된 기록은 여기서 보이지 않아요. | 표시 개수 제한으로 인해 오래된 기록 일부는 표시하지 않았습니다. |
| 4 | 정답은 ku예요. 이번 라운드에서 한 번 더 나와요. | 틀렸어요! 더 집중하세요. |
| 4 | 고르지 않아도 괜찮아요. | 먼저 이해도를 선택해야 합니다. |
| 5 | 진행 중인 학습이 없어요. | 열린 세션이 없습니다. |
| 5 | 지금 연결이 원활하지 않아요. | 5xx 응답 / Transient error |
| 6 | 지금은 준비된 문장이 없어요. 잠시 후 다시 시도해 주세요. [다시 시도하기] | 준비된 문장 없음 |

사용자가 **스스로** 누르는 표시(`맞았어요`/`틀렸어요`)는 탓하는 말로 보지 않는다. 앱이
판정하는 곳(가나 `보고 고르기`)에서는 `틀렸어요` 대신 정답을 알려 주는 문장을 쓴다(원칙 4).

### 화면 문구 표

화면 문구의 canonical 목록이다. `고정`은 동작 규칙과 함께 그 절이 문구를 정한다는 뜻이고
(문구는 그 절에 있다), `보안`은 의미를 반드시 유지한다는 뜻, `서버 값`은 서버 payload나
서버 숫자에서 온다는 뜻이다. `{}`는 값이 들어가는 자리다.

## 화면 전환과 시트

움직임은 **자체 CSS**(transition, @keyframes, class 토글)로 만든다. 프레임워크·애니메이션
라이브러리를 추가하지 않고 **View Transitions API를 쓰지 않는다.** 시각 참고는
`spec/reference/ui/mvp-02-mockup.html`이며 값은 아래가 canonical이다.

``` text
frontend/src/styles.css    motion 토큰, reduced-motion 미디어 쿼리 안의 토큰 치환
frontend/src/ui/screen.ts  showScreen(root, screen, signal)   화면 교체
frontend/src/ui/sheet.ts   openSheet(options) -> SheetHandle  바텀시트
frontend/src/ui/topbar.ts  renderTopBar({ onHome, onLogin?, actions })  상단바 레이아웃 (동작은 주입받는다)
```

-   **논리 상태는 애니메이션 이벤트를 기다리지 않는다.** 화면 교체는 즉시 DOM을 바꾸고 나가는 화면을
    애니메이션하지 않는다. 시트를 닫으면 포커스 복귀와 다음 조작 가능이 즉시 일어나고 시각적 숨김만
    transition 끝에서 한다. 그 이벤트가 오지 않아도(reduced-motion, 테스트) 조작이 막히지 않는다.
-   reduced-motion은 CSS 미디어 쿼리 안에서 토큰을 바꾸는 것으로 끝낸다. JS로 미디어 쿼리를 분기하지 않는다.
-   화면 모듈은 root를 직접 비우지 않고 `showScreen`을 쓴다. 다른 화면으로 떠난 뒤(`signal`이 abort된 뒤)
    늦게 온 응답이 화면을 바꾸지 못하게 하기 위해서다. 화면을 바꾸면 맨 위로 즉시 스크롤하고 제목에
    포커스를 둔다.
-   문서 수준 리스너는 `frontend/src/routes.ts`의 `hashchange` 하나다. 시트의 Esc는 시트 요소에 단다.

### motion 토큰

``` text
빠름    120ms                      누름 반응, 색·배경 변화, 토글 스위치
기본    240ms                      가림막 페이드, 패널 전환, 토스트 투명도, 번역 펼침
느림    360ms                      화면 진입, 시트 올라오기
easing  cubic-bezier(.2,.9,.25,1)  움직이는 것 (시트, 토스트, 화면 진입)
easing  ease                       색·투명도·누름 반응
```

토큰 이름은 구현이 정한다. 튀어 오르는(overshoot) 곡선과 축하 연출은 두지 않는다. 학습 앱에서
압박으로 읽힐 수 있고, 세션 종료에 연출을 붙이지 않는 규칙과 같은 취지다.

### 화면 진입

-   들어오는 화면은 **10px 아래에서 위로 떠오르며 fade**로 나타난다. 360ms 이내다.
-   번역·설명·probe 같은 화면 **안의** 변화에는 화면 진입 움직임을 쓰지 않는다.

### 설명 시트

**item 설명만 시트로 보여준다.** 번역·확인·오류는 시트가 아니다.

-   아래에서 올라온다(느림, 움직이는 easing). 가림막은 투명도만 바뀐다(기본).
-   `role="dialog"`, `aria-modal="true"`, 제목 연결. 닫는 방법은 `닫기` 버튼, 가림막 탭,
    Esc. 열면 시트 제목으로 포커스를 옮기고, 닫으면 시트를 연 표현으로 돌려준다.
-   **시트 내용은 열 때 만든다.**
-   자기평가 버튼은 시트 안에 두며, 누르지 않고 닫아도 된다(`Explanation`).
-   **`explanation_revealed`는 떠나지 않은 학습 화면의 DOM에 설명 내용이 삽입된 시점에 보낸다.** 올라오는
    애니메이션이 끝나기를 기다리지 않는다. `/click` 응답 전에 화면을 떠나 `signal`이 abort됐으면 설명을 그리지
    않고 `explanation_revealed`를 보내지 않는다(`item_clicked`만 남는다). 시점 구분의 canonical은 `05_API_SPEC.md`의 `explanation_revealed를 언제 보내는가`다.
-   **재열기:** 시트를 닫고 같은 표현을 다시 탭하면 이미 받은 설명으로 시트를 다시 연다. `item_clicked`와
    `explanation_revealed`는 presentation + item당 1회이며, 두 번째 탭부터 `/click`을 다시 부르지 않는다
    (같은 절).

### 번역 인라인 펼침

-   번역은 시트가 아니다. `문장 뜻 보기`를 누르면 **문장 바로 아래에 부드럽게 펼쳐지는 인라인
    영역**에 나온다. 문장과 번역을 함께 보기 위해서다.
-   번역 DOM은 **reveal 응답을 받은 뒤에만** 만든다. 숨겨 둔 번역 노드를 두고 펼치는 구조로
    만들지 않는다(`Translation/Furigana`, `05_API_SPEC.md`의 `Sentence Presentation Payload`).

### 토스트와 오류

-   토스트는 한 번 사라지는 **정보성 안내에만** 쓴다(예: `세션 시작 안내`, `기록했어요`,
    `진도를 초기화했어요`). **4초 뒤 사라지고** 탭하면 바로 닫힌다. `role="status"`.
-   **오류는 토스트로 띄우지 않는다.** 그 자리에 인라인으로 남기고 할 수 있는 행동 버튼을
    붙인다(`문구 가이드` 원칙 6). 사라지는 오류는 사용자가 놓치고 재시도 버튼을 붙일 수 없다.
-   안내는 학습 진행을 막지 않는다(`세션 시작 안내`).

### 누름 반응

-   `:active`에서 `scale(.97~.985)`, 100\~120ms. 요소가 작을수록 더 줄인다.
-   **hover 효과를 두지 않는다.** 기본 탭 하이라이트를 끄는 대신 `:focus-visible` 윤곽선을
    반드시 둔다. `disabled`는 누름 반응이 없다.
-   **tappable 표현은 크기를 줄이지 않는다.** 문장 줄바꿈이 흔들린다. 배경색 변화만 쓴다.

### reduced-motion

`prefers-reduced-motion: reduce`이면 **이동(transform)을 없애고 짧은 fade만 남긴다.**

``` text
화면 진입      페이드만 (빠름)
설명 시트      이동 없이 페이드만 (빠름, 가림막 포함)
번역 펼침      페이드만
토스트         페이드만
누름 반응      scale 없음, 배경색 변화만
진행바         즉시
```

### 후리가나 토글

스위치 손잡이와 색만 움직인다(빠름). 후리가나를 켜고 끌 때 **문장에는 애니메이션을 주지
않는다.** 줄 높이가 바뀌어 글자가 튀어 보인다.

## 상단바

**모든 화면에 있다.** 왼쪽은 앱 이름 `Nihongo Context`이고 누르면 선택 홈으로 간다.

| 화면 | 오른쪽 |
|---|---|
| 선택 홈, 가나 학습 | `로그인` |
| Demo | 후리가나 토글, `로그인` |
| Login | 없음 |
| Study Screen | `학습 기록`, `로그아웃`, 후리가나 토글 |
| History | `로그아웃` (문장이 없어 후리가나 토글이 없고, `학습 기록`은 자기 자신이라 없다) |

-   Study Screen의 메뉴는 MVP-01에서 화면 안에 있던 `학습 기록` 링크와 `로그아웃` 버튼을
    상단바로 옮긴 것이다. 메뉴를 새로 늘리지 않는다(`로그아웃`).
-   Login 화면의 오른쪽은 비운다. History의 화면 내용(두 목록과 `학습으로 돌아가기`)은 그대로이고, 상단바의
    `로그아웃`은 화면 내용이 아니라 로그인 영역 공통 틀의 메뉴다(`로그아웃`).
-   앱 이름을 눌러 선택 홈으로 가도 **study session을 닫지 않는다.** 로그아웃이 study session을
    닫지 않는 것과 같은 이유다(`로그아웃`).
-   후리가나 토글은 문장이 있는 두 화면(Study Screen, Demo)의 상단바에만 둔다.
-   `ui/topbar.ts`는 레이아웃만 만들고 버튼은 각 영역이 만든 요소를 받는다. 그래서 상단바 모듈이
    로그아웃 코드(API)를 import하지 않는다.

### 로그인 진입

-   **공개 화면을 열 때 로그인 상태를 확인하지 않는다.** 상단바 `로그인`을 **누를 때만**
    `GET /api/auth/me`를 한 번 부른다(불변식 14, `01_USER_FLOW.md`의 `Private Learning`).
    그래서 쿠키가 유효한 사용자에게도 공개 화면의 오른쪽은 `로그인`이다.
-   누르면 다음 순서다(`frontend/src/main.ts`의 로그인 진입).

    ``` text
    1  지금 화면을 떠난다(그 화면의 signal abort)
    2  hash가 있으면 history.replaceState로 지운다 (hashchange 없음)
    3  로그인 영역 모듈 frontend/src/private.ts를 동적 import한다
       실패(청크 적재 실패, 오프라인, 배포로 옛 청크가 사라짐) -> 홈 자리에 인라인 안내만 (버튼 없음)
         "로그인 화면을 불러오지 못했어요. 위의 로그인을 다시 눌러 주세요."
    4  enterPrivate: GET /api/auth/me
         200         Study Screen (세션 생성/재개는 01_USER_FLOW.md)
         401         Login
         그 밖의 실패 인라인 안내 + [다시 시도하기]. 공개 화면은 그대로 쓸 수 있다
    ```

-   `fetchMe`를 부를 수 있는 코드는 `private.ts`의 import 그래프 안에만 있고, 그 그래프로 들어가는 간선은
    `main.ts`의 이 동적 import 하나다. 불변식 14는 분기 순서가 아니라 **격리 검사와 런타임 단정으로** 지킨다
    (`spec/04_SECURITY_AND_DATA.md`의 `격리 검사 (MVP-02 확정)`).
-   **로그인 진입(`openLogin`)은 `ui/topbar.ts`의 로그인 버튼 `click` 리스너 안에서만 불린다.** 공개 화면은
    `renderTopBar`의 `onLogin`으로 넘기기만 하고, 상단바가 `onLogin`이 있을 때 오른쪽에 `로그인` 버튼을 만든다.
    부팅·route 적용·타이머에서 불리지 않는다.
-   **떠난 화면은 새 화면 진입 요청을 시작하지 않는다.** `signal`이 abort되었으면 화면 전환뿐 아니라 새 화면에
    들어가는 요청(3의 동적 import 뒤 `fetchMe`, study session 시작)도 시작하지 않는다. 진행 중 학습의 event 전송과
    재시도는 `05_API_SPEC.md`의 규칙(설명 표시는 `explanation_revealed를 언제 보내는가`)을 따른다
    (`spec/04_SECURITY_AND_DATA.md`의 `모듈 경계`와 같다).

-   확인 중에는 버튼을 비활성으로 두고 `확인 중`으로 적는다. 연속으로 눌러 요청이 겹치지 않는다.
-   로그인 진입이 불러오는 코드는 공개 화면의 import 그래프에 들어가지 않는다. 공개 화면 모듈은
    로그인 진입 동작을 `main.ts`에서 주입받는다(불변식 13,
    `spec/04_SECURITY_AND_DATA.md`의 `공개 화면 셋으로 확장 (MVP-02 확정)`).
-   로그인 영역 안의 이동(Login → Study → History)은 콜백이고 hash를 바꾸지 않는다.

### 화면 이동

-   공개 화면은 hash route를 가진다.

    ``` text
    hash                       화면        적재
    '' 또는 #/                 선택 홈     정적
    #/demo                     Demo        동적 import
    #/kana, #/kana/<하위>      가나 학습   동적 import
    그 밖의 hash               선택 홈     정적. history.replaceState로 URL을 #/로 바꾼다
    ```

-   `hashchange`를 듣는다(`frontend/src/routes.ts`가 유일한 리스너). 브라우저 뒤로 가기는 **공개 화면
    사이에서만** 보장한다. 로그인 영역에서 뒤로 가기는 보장하지 않으며 선택 홈으로 가는 길은 상단바 앱
    이름이다.
-   공개 route는 `routes.ts`의 route 표에 등록한다. 각 화면 모듈은 `mount(ctx)` 하나를 내보내고, `ctx`는
    `root`, `signal`, `subpath`(`#/kana/hiragana` → `hiragana`), `navigate`, `openLogin`을 준다.
-   Login, Study Screen, History는 **hash route를 두지 않는다**(메모리 상태). 이 화면들에서
    새로고침하면 선택 홈이 뜬다. 다시 `로그인`을 누르면 쿠키가 유효하므로 곧바로 Study Screen으로
    간다.
-   로그아웃하면 선택 홈으로 간다(`로그아웃`).
-   **`#/kana` 하위 경로는 메뉴 수준(예: 히라가나/가타카나 선택)에만 쓴다.** 하위 hash가 바뀌면 가나 학습
    화면이 다시 mount되므로 퀴즈 라운드 진행 상태는 hash에 두지 않는다. 하위 경로의 이름은 가나 학습 구현이
    정한다.
-   **URL에서 온 값(hash, 하위 경로)은 고정 허용 목록과 비교만 하고 화면에 그대로 출력하지 않는다.** 화면은
    HTML 문자열 삽입 없이 `textContent`와 요소 생성으로만 만든다(`spec/04_SECURITY_AND_DATA.md`의
    `HTML 삽입과 URL 값 (MVP-02 확정)`).
-   **"서버 요청 0건"의 서버는 API origin이다.** 공개 route에 들어갈 때 frontend origin에서 화면 청크·아이콘·
    manifest를 받는 것은 정적 자산이며 여기에 들지 않는다.
-   PWA의 시작 주소는 그대로 `/`다. 설치한 앱을 열면 선택 홈이고, 계정 사용자는 `로그인`을 한 번 누른다.

## 선택 홈

hash가 없거나 `#/`일 때의 첫 화면이다. **방문자가 무슨 앱인지 바로 알 수 있어야 한다.**

``` text
상단바       Nihongo Context · 로그인
한 줄 소개   (문구 표)
카드 1       표현 학습 체험해 보기 → #/demo
카드 2       글자부터 배우기       → #/kana
```

-   문구는 `문구 가이드`의 `화면 문구 표`를 따른다.
-   **서버 요청 0건이고 API 모듈을 import하지 않는다**(불변식 13). 로그인 상태도 확인하지 않는다
    (`상단바`).
-   **카드에 문장 수 숫자를 적지 않는다.**
-   선택 홈 모듈(`frontend/src/home/`)은 `main.ts`의 정적 그래프 안에 있다. demo와 가나 학습 코드는 각 route의
    동적 import로만 불러온다.
-   로그인·계정 관리·통계로 가는 카드를 두지 않는다.

## Login

`01_USER_FLOW.md`의 `Authentication check`에 대응하는 화면이다. MVP-02에서는 상단바
`로그인`을 눌러 확인한 결과가 401일 때 이 화면으로 온다(`상단바`의 `로그인 진입`). **폼은 두
필드와 버튼 하나가 전부다.**

``` text
login_id     텍스트 입력
password     비밀번호 입력 (마스킹)
[로그인]     POST /api/auth/login
```

-   실패 응답은 사유와 무관하게 같은 401이므로(`05_API_SPEC.md`) 화면도
    **하나의 문구**만 보여준다. "없는 아이디"와 "틀린 비밀번호"를 갈라
    적으면 서버가 감춘 것을 UI가 알려주게 된다.
-   회원가입·비밀번호 재설정·소셜 로그인 진입점을 두지 않는다. public
    signup이 없고 계정은 CLI로만 만들기 때문에(`04_DB_SPEC.md`) 누를 대상이
    되는 endpoint 자체가 MVP에 없다.
-   password 길이 규칙을 이 화면에 적지 않는다. 검증은 계정 생성 경로에만
    있고 login은 검증하지 않는다(`05_API_SPEC.md`).
-   성공하면 Study Screen으로 이동한다. Demo는 로그인 없이 접근하므로 이
    화면을 지나지 않는다. 선택 홈과 가나 학습도 같다.
-   **폼 안에 demo 진입 버튼을 두지 않는다.** MVP-01 구현에 있던 폼 안의 demo 버튼은 없앤다.
    선택 홈으로 가는 길은 상단바의 앱 이름이다(`상단바`). 폼의 두 필드와 버튼 하나는 그대로다.
-   실패 문구는 `문구 가이드`의 `화면 문구 표`에 있으며 사유를 가르지 않는 한 문구라는 의미를
    유지한다.

## Study Screen

모바일이 주 사용 환경이므로 한 손 조작과 짧은 세션을 우선한다.

MVP Study Screen에는 **audio/듣기 control이 없다**(`00_SCOPE.md`).

### 진행 표시

진행바의 분자·분모와 "세션 종료 도달"의 판정식은 `05_API_SPEC.md`의
`진행 상태의 갱신과 세션 종료 판정`이 canonical이다. 화면 쪽 요구는 셋이다.

-   진행은 **문장 단위로** 갱신한다. `/complete` 직후
    `GET /api/study/session`을 한 번 다시 읽는다. 문장을 읽는 동안 진행바가
    멈춰 있는 것은 정상이다 --- `active_seconds`는 상호작용 사이의 시간을
    누적한 값이고, 멈춘 화면은 그 정의를 그대로 보여주는 것이다.
-   **주기적 폴링을 하지 않는다.** 진행바를 매끄럽게 만들려고 상호작용
    endpoint를 주기 호출하면 자리를 비운 시간이 학습 시간으로 누적된다(같은
    절). 진행바의 부드러움을 위해 `active_seconds`의 의미를 바꾸지 않는다.
-   **화면에 쓰는 분 수는 서버가 준 숫자만이다.** `오늘 약 12분`의 출처는 응답의
    `target_minutes`이고 연장분은 `extended_minutes`다. config 값을 frontend에
    복사하지 않는다. 서버가 주지 않는 숫자는 아래 `Session End`처럼 문구에서
    **뺀다.**

### 세션 시작 안내

`POST /api/study/session`은 세 결과 중 하나이고, 화면은 그것을 **한 번 사라지는
안내**로 알린다. 문구는 다음으로 고정한다.

``` text
resumed = true                    이어서 학습해요.
timed_out_session_id != null      한동안 쉬어서 새로 시작해요.
                                  지난 기록은 그대로 있어요.
그 밖 (새 session, timeout 아님)  안내 없음
```

MVP-02에서 두 문구를 `문구 가이드`에 맞춰 해요체로 바꿨다. 뜻과 아래 제약은 그대로다. 안내는
토스트로 띄운다(`화면 전환과 시트`의 `토스트와 오류`).

-   **두 안내는 동시에 나오지 않는다.** `resumed = true`인 응답의
    `timed_out_session_id`는 항상 `null`이다 --- resume은 열린 session을 그대로
    돌려주는 경로이므로 닫은 session이 없고, timeout은 그 session을 닫고 **새** session
    을 만드는 경로이므로 `resumed = false`다. 두 값은 배타적이므로 화면에 우선순위
    규칙이 필요하지 않다.
-   처음 시작하는 세션에는 안내를 띄우지 않는다. 알릴 것이 없다.

세 경우 모두 다음 제약을 지킨다.

-   경고나 오류로 보이게 하지 않는다. 사용자가 잘못한 것이 없고 학습 기록도 그대로
    남아 있다. overdue/streak punishment 금지와 같은 취지다.
-   내부 id를 화면에 노출하지 않는다(`timed_out_session_id`, `session_id`).
-   **복귀나 확인 동작을 요구하지 않는다.** 안내를 닫는 것 외에 누를 것이 없고,
    안내가 학습 진행을 막지 않는다.

timeout 경우에만 해당하는 것 하나: **지난 세션으로 돌아가는 동작을 제공하지
않는다.** 그 session은 이미 닫혔고 남은 문장은 영원히 미완료다(`05_API_SPEC.md`의
`세션·presentation 상태 게이트`).

## Explanation

cached/precomputed. canonical expression, reading, type, 핵심 뜻 1\~2개,
현재 문맥 뜻, 짧은 nuance, 예문 1개. 하단 self-report는 선택적.

tap 즉시 표시하며 **live LLM을 호출하지 않는다.** 설명이 없는 item이
포함된 문장은 애초에 Ready Pool에 들어가지 않는다(`08_LLM_SPEC.md`).

설명 패널이 실제로 렌더된 직후에 `explanation_revealed`를 보낸다. `item_clicked`와
시점이 다른 이유(탭했으나 설명이 표시되지 않은 경우를 구분한다)와 횟수 규칙은
`05_API_SPEC.md`의 `explanation_revealed를 언제 보내는가`가 canonical이다. MVP-02의 설명
시트에서 그 시점은 설명 내용이 DOM에 삽입된 시점이고, 재열기 규칙과 함께 `화면 전환과 시트`의
`설명 시트`에 있다.

**설명의 읽기 표시(MVP-02):** 설명 머리에는 **문장 속 표면형과 그 읽기**를 짝지어 보여준다
(예: 문장의 `任せ`와 `まかせ`). 기본형(`canonical_form`, 예: `任せる`)은 따로 적는다. 읽기는
데이터에 있는 `reading`을 그대로 쓰며, **기본형의 읽기를 화면이 새로 만들지 않는다.** 이
읽기와 문장 위 후리가나의 관계는 `Translation/Furigana`에 있다.

### tappable span 표시

**tappable span은 전부 같은 방식으로** 지나치게 시험 문제처럼 보이지 않게
subtle하게 표시한다. 학습 대상(target)인 span과 그렇지 않은 span을 시각적으로
구분하지 않으며, 그 구분을 알려주는 필드를 `tappable_items` payload에 두지도
않는다(`05_API_SPEC.md`의 `Sentence Presentation Payload`).

-   대상만 강조하면 그 문장에서 무엇이 평가 대상인지가 드러나 "지나치게 시험
    문제처럼 보이지 않게"가 그 자리에서 무너진다.
-   강조된 span만 눌리게 되어 incidental click 경로가 사실상 사라진다. 그 경로는
    사용자가 target이 아닌 표현을 눌러 `몰랐음`/`애매함`을 고르는 것이고
    (`02_LEARNING_POLICY.md`의 `Incidental Item Click`), MVP에서 신규 학습
    target이 생기는 주된 통로다.
-   target 여부는 `user_sentence_candidate_targets`가 가진 서버 측 사실이며
    (`07_SRS_SPEC.md`의 `target item의 canonical 정의`) 화면이 그것을 알 필요가
    없다.

한 문장에 신규 item은 권장 1개, 최대 2개.

## Translation/Furigana

일본어 먼저. 번역 hidden. 번역은 `문장 뜻 보기`를 누른 뒤 문장 아래 인라인 영역에
펼친다(`화면 전환과 시트`의 `번역 인라인 펼침`).

MVP-01의 "furigana 상시 표시 금지"는 MVP-02에서 아래 규칙으로 바뀌었다. item tap 후 설명에서
reading을 제공하는 규칙(`Explanation`)은 그대로다.

### 후리가나 표시 규칙

-   **기본은 끔이다. 사용자가 켤 수 있다.** 켜면 학습 문장 안의 **모든 한자**에 읽기를
    표시한다. 학습 표현이 아닌 한자(예: `仕事`, `田中`)에도 단다. 문장 자체를 읽을 수 있게 하기
    위해서다.
-   **"모든 한자"의 예외.** 틀린 읽기를 보이는 것보다 비워 두는 쪽을 택한다. 다음 토큰의 한자에는
    읽기를 달지 않는다(그 토큰의 한자 전부를 비운다).

    ``` text
    수사와 바로 뒤 조수사   一点, 三十分, 2人 같은 수 묶음 (음변화를 사전 읽기가 틀리게 낸다)
                           사전에 한 토큰으로 있는 수 표현(一人 ひとり, 二人 ふたり)은 달린다
    사전에 읽기가 없는 한자  분석기가 읽기를 내지 못한 한자
    tappable 경계를 넘는 토큰 읽기를 달면 탭 가능한 표현의 경계를 넘게 되는 토큰
    ```

    seed 기준으로 한자 문자의 약 2%가 첫 번째 예외에 해당했다. 규칙의 canonical은 ADR-021이다.
-   화면은 **저장된 ruby를 표시만 한다.** 브라우저에서 읽기를 계산하지 않는다(불변식 15).
    저장된 ruby가 없는 한자에는 표시하지 않는다. 위 예외, 아직 계산하지 않았거나 계산에 실패한
    문장, 저장값이 검증을 통과하지 못한 문장이 여기에 해당하며, 화면은 이 경우들을 구분하지 않는다
    (`05_API_SPEC.md`의 `render_segments[].ruby`).
-   분석기의 체계적 오독은 계산 단계의 교정 계층(tappable 표현은 설명의 `reading` 우선, 그 밖은 저장소에
    커밋된 작은 교정 표)으로 줄인다. 그래도 탭할 수 없는 한자의 문맥 의존 읽기는 틀릴 수 있다(ADR-021).
-   **표시 범위는 학습 문장뿐이다.** 설명 시트의 예문, `canonical_form`, probe의 표현 표기에는
    달지 않는다(그 자리의 ruby 데이터가 없다).
-   **probe 중에도 그대로 표시한다.** probe는 자기평가이고 읽기는 뜻이 아니기 때문이다.
-   로그인한 Study Screen과 Demo에서 **똑같이 동작한다.** Study Screen의 토글은 상단바에
    있다. Demo의 토글도 상단바에 있다(`상단바`).

### 설정

-   켬/끔은 **브라우저 localStorage에만** 저장한다. DB·API·config에는 없다
    (`spec/04_SECURITY_AND_DATA.md`의 `localStorage 사용 범위 (MVP-02 확정)`).
-   Study Screen과 Demo가 **설정 하나를 공유한다.** 한쪽에서 켜면 다른 쪽도 켜져 있다.
-   저장을 쓸 수 없으면 끔으로 시작하고, 그 페이지 안에서는 토글이 정상 동작한다.
-   이 설정은 `14_CONFIGURATION.md`의 `reading_default_visible`과 다른 것이다(같은 문서의 설명).
-   key는 `nc.furigana.v1`, 값은 `{"on": boolean}`이다. 저장값이 정확히 `{"on": true}`일 때만 켬이고, 없거나
    형식이 틀리거나 읽을 수 없으면 끔이다.
-   설정과 토글은 `frontend/src/ui/furigana.ts` 한 모듈이 맡는다.

    ``` ts
    export const FURIGANA_ON_CLASS = 'furigana-on'   // document.documentElement에 붙는 class
    export function isFuriganaOn(): boolean
    export function setFuriganaOn(on: boolean): void // 저장하고 class를 전환한다. 요청·event 없음
    export function renderFuriganaToggle(): HTMLElement // 상단바 actions에 넣는 토글 버튼(aria-pressed)
                                                         // 만들 때 저장값을 문서 class에 적용한다
    ```

-   부팅 hook이 없다. 문장이 있는 화면이 상단바에 토글을 넣을 때 저장값이 적용된다. CSS 기본값이 숨김이라
    설정을 읽기 전에 읽기가 번쩍 보이지 않는다.

### 토글과 렌더링

-   토글은 **CSS class 전환**으로 한다(`rt` 숨김/표시). class는 `document.documentElement`에 두고 CSS
    선택자는 학습 문장 안의 `rt`로 한정한다. 토글할 때 문장을 다시 렌더링하지 않고, tappable span의
    상호작용 handle을 다시 만들지 않는다. 그래서 ruby 요소는 설정과 무관하게 렌더되고 표시만 class로
    바뀐다.
-   **ruby 표시가 원문 문자열, codepoint 좌표, tappable span 경계, 번역 reveal 규칙을 바꾸지
    않는다**(불변식 17). ruby는 tappable span 경계를 넘지 않게 저장되어 있으므로(ADR-021) 화면은
    span 안에서만 ruby를 그린다. 문장 텍스트를 비교할 때는 `rt`의 읽기를 빼고 비교한다.
-   후리가나 표시와 토글은 **학습 신호가 아니다.** event·exposure·evidence를 만들지 않고 서버로
    보내지 않는다(`02_LEARNING_POLICY.md`의 `학습 신호가 아닌 것 (MVP-02)`).

-   **렌더링:** 공통 문장 렌더러 `renderSentence(segments, onTapItem)`(`frontend/src/ui/segments.ts`)의
    시그니처는 바꾸지 않는다. segment의 `ruby`(`05_API_SPEC.md`의 `render_segments[].ruby`)가 비어 있으면
    지금처럼 text만 넣고, 그 밖이면 part마다 `reading`이 null이면 텍스트 노드, 아니면
    `<ruby>text<rt>reading</rt></ruby>`를 만든다. tappable이면 그 조각들이 표현 버튼 안에 들어간다.
    `rt`는 **항상** 만든다. 렌더러는 토글 상태를 모른다.
-   문장의 `aria-label`은 segment의 text만 이은 원문이다. 읽기를 넣지 않는다.
-   demo fixture의 segment도 같은 `ruby` 형식이다(`Demo`의 `fixture`).

### 후리가나와 item 설명 reading의 관계

``` text
후리가나          문장 속 모든 한자의 읽기. 표시 보조. 형태소 분석기가 적재·생성 시점에 계산
item 설명 reading 탭한 item의 읽기. 설명의 일부. seed·LLM이 만든 설명 데이터(Explanation)
```

-   둘은 출처가 다르고 **서로를 대신하지 않는다.** 후리가나를 켜도 item 설명의 reading은 그대로
    tap 뒤 설명에서 나온다.
-   둘이 어긋날 수 있다. **자동으로 고치지 않는다.** 어긋남은 보고 목록으로만 남긴다
    (`11_OBSERVABILITY.md`의 `MVP-02 추가: 후리가나 계산 결과`).

## Session End

`오늘 학습 완료 / 더 학습하기`. overdue/streak punishment 금지.

이 선택지를 언제 띄우는지는 `05_API_SPEC.md`의
`진행 상태의 갱신과 세션 종료 판정`이 canonical이다. 도달했다는 것은 세션이
닫혔다는 뜻이 아니므로 화면을 강제로 전환하지 않는다 --- 사용자가 `오늘 학습 완료`를
누르면 `/finish`, `더 학습하기`를 누르면 `/extend`이고, 둘 다 누르지 않으면 현재
문장을 계속 읽을 수 있다.

**연장 버튼 문구에 분 수를 적지 않는다.** 연장 폭은 서버의
`extra_session_minutes`(`14_CONFIGURATION.md`)이고, 그 값은 `/extend`를 호출하기
전 어떤 응답에도 실려 있지 않다(`05_API_SPEC.md`). 그래서 화면에 `+5분 더`라고
적으면 그것은 **정책값 하드코딩**이다. config를 6분으로 바꾸는 순간 화면은 계속
`5분`이라 말하고 서버는 6분을 더하는데, 그 불일치를 잡는 테스트가 없다. v0.2의
`+5분 더`는 이 이유로 철회한다.

-   같은 규칙이 `오늘 약 12분`을 허용하는 이유는 그 숫자가 응답의
    `target_minutes`로 내려오기 때문이다(위 `진행 표시`). 규칙은 **"서버가 준
    숫자만 화면에 쓴다"** 하나이고, 두 문구의 처리가 갈리는 것은 그 규칙의
    결과다.
-   `01_USER_FLOW.md`와 `spec/03_DOMAIN_MODEL.md`의 `+5분`은 config **기본값**을
    가리키는 서술이며 화면 문구가 아니다.
-   연장이 실제로 얼마였는지는 `/extend` 응답의 `extended_minutes`로 확인되고,
    그 값이 곧 진행바 분모를 갱신한다(위 `진행 표시`). 사용자가 "얼마나 늘었나"를
    알 수 있는 지점은 **누른 뒤**이며, 그 숫자는 서버가 준 것이다.
-   `StudySessionPayload`에 연장 폭을 노출하는 API 변경은 하지 않았다. 이 화면이
    누르기 **전에** 정확한 분 수를 보여야 한다고 요구하는 조항이 어디에도 없고,
    세션 길이 자체를 `오늘 약 12분`처럼 근사로 제시하는 문서 전체의 어조와도
    어긋나지 않는다. 요구가 생기면 API를 먼저 고친다.

### 완료 화면

`/finish`가 성공한 뒤의 화면은 **완료 문구 한 줄과 학습 시간 한 줄로 끝난다.**

``` text
오늘 학습을 마쳤어요.
학습 시간 {active_seconds에서 만든 값}
```

MVP-02에서 첫 줄을 `문구 가이드`에 맞춰 해요체로 바꿨다. 두 줄로 끝난다는 규칙은 그대로다.

-   숫자는 `/finish` 응답의 `active_seconds` 하나다. 위 `진행 표시`의 규칙
    **"서버가 준 숫자만 화면에 쓴다"**가 여기에도 적용된다. 초를 분으로 반올림해
    보여주는 것은 표현이고, 없는 값을 계산해 넣는 것은 금지다.
-   **새 세션 시작 버튼을 두지 않는다.** 방금 `오늘 학습 완료`를 누른 사용자에게
    `POST /session`을 권하는 화면이 되면, 눌릴 때마다 session 행이 하나 더 생겨
    **history의 세션 기록이 부풀고**(`05_API_SPEC.md`의 `History`) "한 번 더
    하시죠"라는 압박으로 읽힌다. 후자는 이 절이 이미 금지한
    overdue/streak punishment와 같은 종류다. 이 선택은 새 규칙이 아니라 그 금지의
    결과다.
-   그래서 **완료 후에 막히는 경로는 없다.** 다시 학습하려면 앱을 다시 열거나
    새로고침하면 되고, 그때 `POST /api/study/session`이 새 session을 만든다(idle
    timeout 이내에 같은 날 다시 들어와도 방금 세션은 이미 닫혀 있으므로 resume이
    아니라 신규다). 사용자가 명시적으로 다시 시작하는 동작과 화면이 권하는 동작을
    구분하는 것이 요점이다. MVP-02에서는 다시 열거나 새로고침하면 선택 홈이 뜨고, 상단바
    `로그인`을 눌러 Study Screen으로 들어갈 때 `POST /api/study/session`이 불린다
    (`상단바`의 `화면 이동`). 사용자가 명시적으로 누르는 동작이라는 점은 같다.
-   통계·streak·정답률·이번 세션 요약을 넣지 않는다(`00_SCOPE.md`의
    `advanced analytics`, `social/gamification`). 학습 기록을 보려면 `History`로
    간다.

## History

사이드바의 `학습 기록`에 대응하는 화면이다. `00_SCOPE.md`의 `기본 history`가
전부이며 **두 목록으로 끝난다.**

``` text
최근 세션    GET /api/history/sessions
학습한 표현  GET /api/history/items
```

-   `최근 세션`은 한 행에 날짜, 학습 시간, 완료한 문장 수를 보여준다. 진행 중인
    세션은 종료 시각 자리에 `진행 중`을 적는다(`ended_at`이 `null`이다).
-   `학습한 표현`은 한 행에 표현(`lemma`), 노출 횟수, 다음 복습 시점을 보여준다.
    `comprehension_mastery`가 `null`인 행은 숫자 대신 **`아직 평가 없음`**으로
    적는다. 0%로 표시하면 "능력이 0"으로 읽히는데 그 값의 뜻은 "아직 evidence가
    없음"이다(`02_LEARNING_POLICY.md`).
-   고정 상한(`05_API_SPEC.md`의 `개수 상한`)에 걸려 목록이 잘리면 그 사실을 목록
    끝에 한 줄로 적는다. 잘린 것을 숨기면 사용자가 기록이 사라졌다고 읽는다. **더
    보기·기간 선택·검색·정렬 변경을 두지 않는다.**
-   그 문구는 응답의 `truncated`가 `true`일 때만 띄운다(`05_API_SPEC.md`의
    `truncated`). **받은 행 수로 추측하지 않는다** --- 행이 정확히 상한만큼인
    사용자에게 잘렸다고 거짓을 말하게 된다.
-   통계·차트·표현별 상세 화면을 두지 않는다(`00_SCOPE.md`의
    `advanced analytics`). 여기서 다음 행동으로 이어지는 버튼도 두지 않는다 ---
    학습은 Study Screen에서만 일어난다.
-   Reference mockup 사이드바의 `표현 보관함`과 `설정`은 **MVP 화면이 아니다.**
    `00_SCOPE.md`에 해당 기능이 없고 그것을 지탱하는 API도 없다.

## 로그아웃

`POST /api/auth/logout`(`05_API_SPEC.md`의 `Authentication`)에 대응하는
**버튼 하나**다. 새 화면을 만들지 않는다.

``` text
화면   Study Screen과 History의 상단바 (MVP-02). 그 밖의 화면에는 두지 않는다
위치   상단바 오른쪽. Study Screen에서는 `학습 기록` 옆 (위 `상단바`)
문구   로그아웃
동작   POST /api/auth/logout -> 성공하면 선택 홈으로 이동 (MVP-02)
```

MVP-01의 위치는 "화면 위쪽, `학습 기록` 링크 바로 아래", 이동은 "Login 화면"이었다. MVP-02에서
`학습 기록`과 함께 상단바로 옮기고, 첫 화면이 선택 홈이 되었으므로 로그아웃 뒤에도 선택 홈으로
간다. History 상단바에도 둔다(아래 문단의 MVP-02 개정).

**`History`에는 두지 않는다.** 그 화면은 `두 목록으로 끝난다`이고 같은 절이
"여기서 다음 행동으로 이어지는 버튼도 두지 않는다"를 이미 정했다. 거기에
로그아웃을 얹으면 그 조항의 첫 예외가 되고, 다음 사람이 그 예외를 근거로
컨트롤을 더 붙인다. 치르는 비용은 **탭 한 번**이다 --- `History`의 유일한
출구인 `학습으로 돌아가기`가 항상 화면에 있고 그 다음 화면이 곧 이 버튼이다.
"기기를 잃었을 때 폐기할 수단이 있다"는 목적에는 **한 곳의 진입점으로
충분하다.**

**MVP-02 개정:** 위 문단은 MVP-01의 화면 안 버튼에 대한 판단이다. MVP-02에서 모든 화면에 상단바가 생기면서
로그아웃은 로그인 영역 공통 틀의 메뉴가 되었고, **History 상단바 오른쪽에 `로그아웃`만 둔다**(Wave 1 보완 결정,
2026-09-13). History의 화면 내용은 여전히 두 목록과 `학습으로 돌아가기`로 끝나며, 거기에 다음 행동 버튼을
더하지 않는다는 조항은 그대로다. 상단바 메뉴를 근거로 History 내용에 컨트롤을 붙이지 않는다.

이것이 MVP 화면인 이유는 `00_SCOPE.md`의 `개인 로그인`이 이미 MVP이고 그
endpoint가 이미 계약에 있기 때문이다. 진입점이 없으면 30일 cookie를
브라우저에서 폐기할 수단이 없어, 기기를 잃거나 공유했을 때 남는 경로가 DB
직접 조작뿐이다. 새 기능을 여는 것이 아니라 **이미 있는 인증 범위를 닫는
것이다.**

-   **확인 대화상자를 두지 않는다.** 잃는 것이 없다 --- 학습 기록은 서버에
    남고 다시 로그인하면 그대로 보인다. 되돌리는 비용이 로그인 한 번이므로
    파괴적 동작이 아니다.
-   **진행 중인 study session을 닫지 않는다.** `logout`이 폐기하는 것은 auth
    session이다. 다시 로그인하면 idle timeout 이내인 세션은 그대로 resume되고
    화면은 위 `세션 시작 안내`의 `이어서 학습해요.`를 띄운다. 그 안내는
    `POST /api/study/session`의 `resumed`가 담당하므로 **로그아웃 경로가 따로
    하는 일은 없다.** 여기에 `/finish` 호출이나 세션 정리를 붙이지 않는다.
-   실패하면 로그인 화면으로 보내지 않고 그 자리에 짧은 안내만 띄운다
    (`10_ERROR_HANDLING.md`). 쿠키가 살아 있는데 화면만 로그아웃된 상태를
    만들지 않는다. **`401`은 예외로 성공과 같게 처리한다** --- 폐기할 세션이
    이미 없다는 뜻이다(`05_API_SPEC.md`).
-   **Demo에는 두지 않는다.** Demo는 Login 화면을 지나지 않으므로 폐기할
    세션이 없다(위 `Login`, 아래 `Demo`). 선택 홈과 가나 학습도 같다.
-   이 버튼과 함께 계정 관리·설정·통계 화면을 만들지 않는다. 위 `History`의
    `설정`은 MVP 화면이 아니라는 조항은 그대로다.

## Demo

Demo임은 알리되 실제 학습 UX와 최대한 동일하게.

Demo는 static frontend fixture로만 동작한다. backend API를 호출하지
않으며 **demo 진도는 그 브라우저의 localStorage에만 저장한다**
(`04_SECURITY_AND_DATA.md`의 `Public Demo 구조 (MVP 확정)`와
`localStorage 사용 범위 (MVP-02 확정)`). MVP-01의 "demo 상태는 browser memory/session 수준에서만
유지한다"는 MVP-02에서 이 규칙으로 바뀌었다.

방문자는 하루쯤 써 보고 떠난다고 본다. 목표는 **충분히 체험할 만한 양**과 **다시 열면
이어서**다.

### 진입과 로딩

-   선택 홈의 카드 1이나 `#/demo`로 들어온다. 상단바 오른쪽은 후리가나 토글과 `로그인`이다(`상단바`).
-   fixture는 **demo route에 들어갈 때 동적 import로** 불러온다. 선택 홈을 가볍게 두기 위해서다.
    route 단위 동적 import(`frontend/src/demo/`의 화면 모듈)로 충족하며, 그 화면 모듈이 fixture를 정적으로
    import해도 둘 다 선택 홈 번들 밖이다. fixture를 한 번 더 동적으로 나누지 않는다. 동적 import가 닿는
    모듈도 API 모듈에 닿지 않는다(불변식 13).
-   불러오기에 실패하면 `화면 문구 표`의 demo 불러오기 실패 문구를 인라인으로 보여준다.

### 체험 요소

``` text
탭 → 설명 시트
번역 reveal (인라인 펼침)
자기평가      알고 있었음 / 애매함 / 몰랐음
probe         알고 있었음 / 애매함 / 몰랐음 / 건너뛰기
다시 보기     같은 문장을 한 번 더
후리가나      Study Screen과 같은 규칙, 설정 공유 (Translation/Furigana)

```

-   **다시 보기는 같은 문장을 다시 보여주는 것이다.** demo는 "새 문맥 재등장(contextual

    `본 문장 수 / 전체 문장 수` 하나이고, 끝은 아래 `완료 화면`이다.
-   화면 동작(설명 시트, 번역 펼침, 후리가나, 문구)은 Study Screen과 같다.
-   화면 위쪽에 체험 안내와 `진도 초기화`를 둔다(문구는 `화면 문구 표`).
-   demo의 어떤 동작도 서버로 가지 않고 학습 신호가 아니다(`02_LEARNING_POLICY.md`의
    `학습 신호가 아닌 것 (MVP-02)`).

### 진행 규칙

프론트엔드의 **단순 규칙**이다. Learning Engine, FSRS, mastery를 프론트엔드에 복제하지 않는다
(불변식 20).

**demo 전용 상수.** 아래 두 값은 체험 흐름의 간격이며 **학습 정책값이 아니다.** 그래서
`14_CONFIGURATION.md`에 두지 않고 서버 config와 연결하지 않는다. 코드에서는
`frontend/src/demo/constants.ts` 한 곳에만 두고, 테스트는 숫자 대신 이 상수를 참조한다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `DEMO_REVIEW_AFTER_SENTENCES` | 5 | 자기평가나 probe에서 "몰랐음/애매함"을 고른 표현이 있는 문장을 5문장 뒤에 한 번 더 보여준다. 문장당 한 번까지 |
| `DEMO_PROBE_EVERY_SENTENCES` | 7 | 7문장마다 한 번 probe를 띄운다 |

1.  **기본 순서는 fixture 순서다**(아래 `fixture`의 문장 순서).
2.  **다시 보기.** 한 문장의 표현에 자기평가에서 "몰랐음"이나 "애매함"을 고르면 그 문장을 다시 보기
    대기열에 넣고, `본 문장 수`가 `DEMO_REVIEW_AFTER_SENTENCES`만큼 늘어난 뒤 한 번 더 보여준다.
    **probe에서 "몰랐음"이나 "애매함"을 골라도 똑같이** 그 표현이 나온 문장을 대기열에 넣는다. 한 문장은
    다시 보기에 **한 번까지만** 들어간다. 신고한 문장도 이 규칙이 그대로다.
3.  **probe.** `본 문장 수`가 `DEMO_PROBE_EVERY_SENTENCES`만큼 늘 때마다 한 번, 앞에서 이미 본
    문장의 표현 중 **자기평가하지 않은 것**을 골라 probe를 띄운다. 후보는 먼저 본 순서로 고른다.
    후보가 없으면 건너뛴다. 같은 표현은 한 번만 묻는다.
4.  **다시 보기로 다시 보여준 문장은 `본 문장 수`에 더하지 않는다.**
5.  **완료**는 fixture의 모든 문장을 한 번 이상 봤고 다시 보기 대기열이 비었다는 뜻이다.

### 진도 저장

``` text
key     nc.demo.v1
값      fixture 식별자, 현재 위치, 표현별 자기평가, 다시 보기 대기열, 본 문장 수
```

-   저장 위치는 **localStorage**다. 서버로 보내지 않고 계정 진도와 합치지 않는다.
-   다시 열면 저장된 위치에서 이어서 보여준다.
-   값 형식은 `frontend/src/demo/`가 정한다. 형식을 호환되지 않게 바꾸면 key의 버전을 올린다
    (`nc.demo.v2`). 옛 key는 옮기지 않는다.
-   **fixture가 바뀐 경우는 key 버전이 아니라 값 안의 fixture 식별자로 판정한다.** 식별자는 fixture 생성
    스크립트가 fixture 내용에서 결정적으로 만든다. 식별자가 다르거나 형식이 맞지 않으면 **조용히 처음부터**
    시작한다. 오류를 띄우지 않는다.
-   모든 접근은 실패할 수 있다고 보고 감싼다. 저장할 수 없으면 **메모리만으로** 정상 동작한다.
-   규칙의 canonical은 `spec/04_SECURITY_AND_DATA.md`의 `localStorage 사용 범위 (MVP-02 확정)`다.

### 진도 초기화

-   체험 안내 옆의 `진도 초기화`를 누르면 그 자리에서 한 번 더 확인한다(`화면 문구 표`). 확인은
    시트가 아니다(`화면 전환과 시트`의 `설명 시트`).
-   초기화하면 demo 진도만 지우고 첫 문장부터 보여준다. 후리가나 설정은 demo 진도가 아니므로
    그대로 둔다.

### 완료 화면

-   위 `진행 규칙` 5번이 성립하면 보여준다.
-   이어서 할 행동 둘을 둔다: `글자 배우기`(→ `#/kana`), `처음부터 다시`(demo 진도를 지우고 첫
    문장부터).
-   문구는 `화면 문구 표`를 따른다. 문장 수는 fixture 길이에서 온다. 통계·정답률을 넣지 않는다.

### fixture

demo 문장은 **`seed/`에서 저장소 스크립트로만** 만든다. 손으로 고치지 않는다. LLM 호출, 새
문장 작성, 비용이 없다.

-   **포함하는 것:** 원문, 번역, tappable span, 설명(`reading`, 핵심 뜻, 문맥 뜻, 뉘앙스, 예문 등
    설명 시트가 표시하는 항목), ruby.
-   **생성할 때 결정적 검사를 적용한다.** 어긋나는 문장은 제외하고 **제외 목록을 출력한다.**

    ``` text
    1  모든 tappable span의 문자열이 원문의 codepoint [start, end)와 일치
    2  모든 tappable item에 설명이 있음
    3  문장당 tappable item 수가 08_LLM_SPEC.md Deterministic Content Validation 5번의 범위
    ```

-   **선택 규칙(greedy set cover).** item을 다음 정렬 키 순서로 돈다.

    ``` text
    difficulty_label (beginner < intermediate < advanced) → frequency_rank → seed_id
    ```

    아직 덮지 않은 item이면, 검사를 통과한 문장 중 그 item을 포함하면서 **아직 덮지 않은 item을
    가장 많이 덮는 문장**을 고른다. 동률은 문장 `seed_id` 순이다. **상한은 200문장이다.**
-   목표는 seed의 모든 표현을 한 번 이상 탭해 볼 수 있게 하는 것이다. 제외된 문장 때문에 상한
    안에서 모든 item을 덮지 못해도 **멈추지 않는다.** 덮지 못한 item 목록을 출력하고 계속한다.
-   **문장 순서는 선택 순서다**(그 문장을 고르게 만든 item의 정렬 키 순서).
-   같은 `seed/`에서는 같은 fixture가 나온다. **커밋된 fixture와 스크립트 재생성 결과가 일치하는지
    테스트한다.** `seed/`가 바뀌면 fixture도 다시 만든다.
-   ruby는 seed 적재·worker와 **같은 계산 함수**(`backend/app/furigana.py`)로 계산하고, segment의 `ruby`는
    API와 같은 분할 함수(`backend/app/render.py`)로 만든다. 그래서 fixture의 segment 형식은
    `05_API_SPEC.md`의 `render_segments[].ruby`와 같다. 분석기 출력과 fixture의 ruby가 일치하는지
    테스트한다.
-   **위치:** 생성 스크립트는 `scripts/build_demo_fixture.py`, 생성 파일은 `frontend/src/demo/` 아래에 둔다
    (파일 이름은 구현이 정한다). 스크립트는 **검사 모드**(쓰지 않고 커밋된 파일과 비교)를 가진다. fixture
    식별자(위 `진도 저장`)도 이 스크립트가 만든다.
-   스크립트는 호스트 `uv run`에서 돈다(분석기가 기본 dependency group에 있다, `spec/02_ARCHITECTURE.md`).
    출력에 제외 목록, 덮지 못한 item 목록, 후리가나 계산 요약을 남긴다(`11_OBSERVABILITY.md`).

프론트엔드만으로 동작하는 히라가나·가타카나 학습이다. 선택 홈의 카드 2나 `#/kana`로 들어온다.

### 퀴즈

**방식은 두 가지뿐이다.** 촉음·장음·외래어는 단어 단위로 묻는다.

``` text
보고 읽기    글자나 단어를 보여준다 → [정답 보기] → 로마자·한글(단어면 뜻)
             → 사용자가 [맞았어요] / [틀렸어요]를 스스로 누른다
보고 고르기  글자나 단어를 보여준다 → 로마자 선택지 4개 중 하나를 고른다
             → 앱이 맞음/틀림을 알려 준다
```

-   `보고 고르기`의 선택지는 **로마자 4개**다. 정답 하나와, **같은 범위**(청음/탁음/…)에서 고른
    오답 셋이며 서로 겹치지 않는다.
-   난수를 쓰는 곳(문항 고르기, 선택지 고르기와 순서)은 **난수를 주입할 수 있게** 만든다.
    테스트가 결과를 고정할 수 있어야 한다.
